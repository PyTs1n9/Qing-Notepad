## 1. 规模与结构

**总量**：VS Code Marketplace 扩展数在 2025 年 5 月突破 **10 万**［官］；到 2026 年第三方全量快照
已达 **约 12.9 万**［研］。VS Code 占开发者使用率 **75.9%**（Stack Overflow 2025），
领先第二名 Visual Studio 46.9 个百分点；VS 与 VS Code 合计月活 **5000 万**［官］。

**平行市场**：Eclipse 基金会运营的 Open VSX 是另一套注册表，服务所有基于 Code-OSS 的
编辑器（Cursor、Windsurf、Kiro、Antigravity、VSCodium、Theia/Ona）。2026 年数据：
**1 万+ 扩展、6500+ 发布者、月下载 3 亿次、峰值日请求 5000 万**［官］。

**结构特征——头部极集中，长尾极长**：

- 顶层不到 30 个扩展吃掉绝大多数安装量（Python 约 1.73 亿、Live Server 约 6500 万、
  Copilot 约 5200–5900 万、Prettier 约 4800 万、Docker 约 4600 万）［估］。
- 尾部数万个扩展安装量在千级以下，从未被搜索到。
- 发布者结构更极端：微软自研扩展约 300 余个，却覆盖了语言支持、调试、远程、容器、
  AI 等全部主干能力；其余数千个发布者分摊剩下的长尾［研］。

**这条"平台方即最大开发者"的事实，决定了后面所有的竞争关系。**

## 2. 类别分布与代表扩展

按 Marketplace 的 20 个类目归并成 8 组。计数为近似值［估］，用于看相对量级而非精确统计。

| 组 | 类目与规模 | 代表扩展 | 解决的问题 | 典型场景 |
| --- | --- | --- | --- | --- |
| **语言与框架** | 语言支持 36,000+ | Python、C# Dev Kit、Java、Go、Rust Analyzer、Volar/vue | 让编辑器认识某门语言：语法、IntelliSense、跳转、重构 | 开一个新语言项目，30 秒内要有补全和报错 |
| **代码片段** | Snippets 19,000+ | ES7 React Snippets、Vue VSCode Snippets | 用缩写展开样板代码 | 写重复的组件骨架、测试模板 |
| **格式化** | Formatters 13,000+ | Prettier、Black、gofmt 集成、Biome | 消除风格分歧，省掉 review 里的空格争论 | 保存即格式化，团队统一风格 |
| **静态检查** | Linters 13,000+ | ESLint、Ruff、SonarLint | 在运行前抓 bug 与坏味道 | 边写边出波浪线，CI 前就修完 |
| **调试与测试** | Debuggers 9,400+ | Python Debugger、C/C++、Debugger for Java、Jest/Vitest | 断点、单步、变量观察；跑单个测试 | 线上问题本地复现、TDD 循环 |
| **版本控制与协作** | SCM Providers | GitLens、GitHub Pull Requests、Live Share | 弄清"这行是谁为什么改的"；协作编辑/评审 | code review 前定位作者与提交 |
| **容器与远程** | 远程开发族 | Dev Containers、Remote-SSH、WSL、Docker | 把环境搬到容器/远端，本地不装依赖 | 新人第一天环境一致；连服务器改代码 |
| **AI 编程** | 增长最快的一组 | GitHub Copilot、Cline、Roo Code、Continue、通义灵码/Comate | 补全、对话、自主改多文件 | 写样板、跨文件重构、让 agent 直接改仓库 |
| **外观** | Themes / Icon Themes / Product Icon | Dracula Official、One Dark Pro、vscode-icons、Material Icon Theme | 降低视觉疲劳、提升文件辨识度 | 长时间盯代码；项目文件太多认不出 |
| **杂项效率** | Other / Keymaps / Language Packs | Todo Tree、Project Manager、Thunder Client、中文语言包 | 单点痛点：TODO 汇总、多项目切换、临时调 API | 「只缺这一个功能」的场景 |

**三个结构性观察**：

1. **语言类是最大宗，但价值密度最低**（36,000 个语言扩展里绝大多数只有语法高亮），
   真正被依赖的是其中极少数带语言服务器的实现。
2. **格式化与静态检查是"必需品"，但因为需求太标准，长期被工具链上游吞掉**
   —— 格式化能力最终都收敛到 Prettier/Biome 这类外部工具，扩展只是胶水。
3. **AI 类是唯一在 2024–2026 年逆势扩张的组**，而且它改变的不是 UI，而是
   "扩展能提供什么"这个问题本身（见第 7 节）。

## 3. 活跃度与维护状况

### 3.1 安装量是累积值，不是当前状态

这是整个生态最被误读的指标。Marketplace 的 install 计数**只增不减**，
所以「300 万安装」可能来自 2015 年的一次爆发。2026 年 10 月基于官方 `extensionquery`
接口的一次实测［研］：

| 扩展 | 安装量 | 最后更新 | 评分 |
| --- | --- | --- | --- |
| Prettify JSON | 297 万 | 2015-12-10 | 2.85★ |
| JSON Tools | 数十万 | 2016 | 4.4★ |
| JSON Crack | 77 万 | 约半年前 | 4.37★ |
| Sort JSON/JSONL | 4.1 万 | 约半年前 | 5.00★ |

两个高安装量的扩展已经停更十年，其中一个评分低到 2.85★ 却仍排在安装量前四。
**安装量在指引用户走向维护最差的代码**，而评分是历史口碑的沉淀，同样不过期。

### 3.2 "已完成"与"被遗弃"无法区分

Marketplace 只有「已弃用」标记（1.68 起提供迁移入口），但一个 2016 年停更的
JSON 排序工具，很可能只是**问题被解决了**（RFC 8259 十年没变），而不是**作者跑了**。
平台不区分这两者，用户也没有工具去区分——只能靠自己在新版本编辑器里试。
这是信息架构的缺失，不是个别扩展的问题。

### 3.3 核心功能吸收：生态的常态化死亡

每当一类扩展验证了需求，官方就有动机把它内置：

| 曾经的必装扩展 | 结局 |
| --- | --- |
| Bracket Pair Colorizer | 括号对着色内置，扩展停更 |
| Auto Close Tag / Auto Rename Tag | HTML/JSX 标签联动内置 |
| Path Intellisense | 路径补全内置 |
| Git 部分能力（blame、历史） | 内置 Git 面板持续增强，GitLens 转向商业化（GitKraken） |
| 部分格式化场景 | 内置格式化 + 语言服务器自带 |

这是**双向的**：它既是生态进化的机制（用户最终受益），也是扩展作者的生存威胁
（做对了就被吞）。理解这一点是判断"哪些扩展值得做"的前提——
**只做核心编辑器行为的扩展，天花板就是被内置**。

### 3.4 性能没有配额

扩展跑在独立的 extension host 进程里，但**没有任何资源配额**。
单个扩展的 file watcher 写不好就能让 16 人团队全部 100% CPU（有公开的团队级复盘）［估］。
平台提供的只有事后诊断工具：`Developer: Startup Performance`、`Developer: Show Running Extensions`、
`code --prof-startup`。`activationEvents: ["*"]`（每次启动立即激活）被官方明确劝阻，
但**没有任何机制阻止它**。

### 3.5 商业可持续性参差

- 头部：GitLens（GitKraken）、Copilot（订阅）、Tabnine/Cursor（订阅）——能赚钱。
- 中腰部：Prettier、ESLint 这类"行业基础设施级"扩展靠赞助和公司背书，扩展本身免费。
- 尾部：大量单人志愿者项目承载百万级安装，靠爱发电，随时可能停更。

**生态把关键路径压在了没有 SLA 的个人项目上**，这是结构性的脆弱点。

## 4. 竞争与互补关系

三种关系同时存在，用同一套视角看会看不清。

### 4.1 替代竞争（同一问题，多个实现）

| 赛道 | 竞争格局 | 胜负手的实质 |
| --- | --- | --- |
| AI 补全 | Copilot（5200 万+）vs Tabnine（本地模型）vs Codeium/Windsurf（免费） | 模型质量 + 订阅价格 + 隐私承诺 |
| AI Agent | Cline（2300 万）vs Roo Code（89 万）vs Continue（160 万）vs Copilot Agent 模式 | 是否 BYOK、能否自主改文件、上下文策略 |
| 中文市场 | 通义灵码（190 万）vs Baidu Comate（31 万）vs Fitten Code（68 万） | 中文语境 + 合规 + 云生态绑定 |
| 格式化 | Prettier（4800 万）vs Biome（Rust，格式+lint 二合一） | 生态兼容性 vs 性能与一体化 |
| 语言服务器 | Pyright / basedpyright / Pyrefly 等多个 Python 实现并存 | 类型检查精度、速度、IDE 绑定关系 |
| 主题 | Dracula / One Dark / 数千个变体 | 几乎没有护城河，靠设计与口碑 |

**AI 赛道的特殊之处**：Cline、Roo Code、Continue 之间是**近乎功能同构**的竞争
（都做 BYOK agent），差异在交互细节和模型接入广度。这类竞争里赢家通吃效应弱，
用户会同时装两三个——也因此这类扩展的安装量虚高，实际使用频率远低于安装量。

### 4.2 协议互补（互相不替代，组合出能力）

这是生态最健康的一层，靠两个外部协议支撑：

- **LSP（Language Server Protocol）**：把语言智能从编辑器剥离。所以
  「Python 扩展 + Pylance + 调试器」可以分别演进，也能被其他编辑器复用。
- **DAP（Debug Adapter Protocol）**：把调试器抽象成统一接口，任何语言的断点体验一致。

协议化带来两个结果：
1. 单一扩展难以垄断某门语言——语言服务器可以换，扩展只是壳。
2. 扩展之间是**拼接关系**：formatter + linter + 语言服务器 + Git 工具，各管一段，
   靠配置（`editor.defaultFormatter`、`eslint-plugin-prettier`）缝起来。

**这也是为什么"全能型 IDE 扩展"很少成功**：协议已经把能力切碎了。

### 4.3 平台吸收（扩展 vs 宿主）

不是扩展之间的竞争，而是**扩展与平台方的竞争**：

- 微软既是 Marketplace 的裁判，又是最大的发布者（约 300 个扩展覆盖全部主干能力）。
- 扩展验证出的通用需求，最终会被内置（见 3.3）。
- 平台还控制 API 的开放节奏：`proposed` API 只对少数合作方开放，
  核心能力（如 chat、agent）优先给 Copilot 链路。

**结论**：在这个生态里，第三方扩展的可持续定位只有三种——
① 垂直领域深度（某框架/某云/某内部系统）；
② 协议适配层（做某个外部工具的桥）；
③ 体验差异化（交互、可视化）。
凡是"通用编辑器行为增强"，都在吸收名单上。

## 5. 风险与不足

### 5.1 供应链攻击的演进链（2023 → 2026）

| 阶段 | 手法 | 检测难度 | 规模 |
| --- | --- | --- | --- |
| 2023 | 名称仿冒（typosquatting），如假 Dracula 主题 "Darcula" | 低 | 一次性，但当时已发现 1,283 个恶意扩展、累计 2.29 亿安装 |
| 2024 | 依赖混淆 + 注册 LLM 常幻觉出的包名 | 中 | 项目级 |
| 2025-09 | Shai-Hulud npm 蠕虫（Chalk/Debug 等周下载 26 亿的包被接管） | 高 | 生态系统级 |
| 2025-10 | **GlassWorm**：首个自传播 VS Code 扩展蠕虫，用不可见 Unicode / 私有区字符藏代码，同时打 Open VSX 与微软 Marketplace | 很高 | 确认 35,800 次安装，窃取 npm/GitHub/Open VSX 凭据、49 种钱包、装 SOCKS 代理与隐藏 VNC |
| 2025-11~12 | 第二三波：伪装成 Flutter/React/Tailwind/Vim 的 48+ 扩展；假 Prettier 通过 Anivia loader 投 OctoRAT | 很高 | 年度 VS Code 相关恶意样本从 27 例涨到 105 例（4 倍） |
| 2026 | **滥用 `extensionDependencies` / `extensionPack` 做传递投递**，前置扩展本身代码干净，静态分析无从下手 | 极高 | Socket 在 Open VSX 识别 72+ 个被感染包 |

关键的两处设计缺陷被反复利用：

1. **扩展默认自动更新**。GlassWorm 全程不需要用户做任何操作，"正常更新"就是投递通道。
2. **凭据就在扩展进程里**。extension host 有完整的 Node 权限，能读 `~/.npmrc`、`~/.gitconfig`、
   环境变量、SSH agent、钱包扩展数据。偷到就能感染下一环，形成蠕虫。

### 5.2 根本问题：崩溃隔离不等于安全隔离

VS Code 的官方文档把 extension host 的定位说得很清楚：**一个崩溃或变慢的扩展
不应该拖垮整个编辑器**。这是可用性隔离，不是权限隔离。

后果是所有扩展都拥有同一套完整权限：
- 能读写用户可访问的任何文件；
- 能执行任意子进程；
- 能发起任意网络请求；
- 能读取工作区外的凭据。

而 `package.json` 里**没有 `permissions` 字段**。用户在安装时看不到"这个扩展要读我的
`~/.ssh`"，因为这份信息根本不存在。这是整个生态最根本的缺陷——比任何单个漏洞都重要。

### 5.3 双信任根的命名空间漏洞

微软 Marketplace 与 Open VSX 是两套独立注册表，同名 `publisher.extension`
在两边可以属于不同的人。2026 年的一次全量对比［研］（12.9 万 vs 1.4 万）：

| 情况 | 数量 | 含义 |
| --- | --- | --- |
| Marketplace 有、Open VSX 无 | **104,456** | 这些名字在 Open VSX 上无人占用，可被任意抢注 |
| 两边发布者不同 | 1,078 | 用户按名字安装会拿到别人的代码 |
| 同 ID 但仓库不同 | 924 | 代码来源被替换 |
| 精确 ID 劫持 | 126 | 含 `sumneko.lua`、`rust-lang.rust` 等百万级扩展 |

对 Cursor / Windsurf 这类只连 Open VSX 的编辑器，**输入完全可信的标识符也可能拿到非原作者代码**。

### 5.4 其他结构性不足

- **无跨编辑器的权限声明标准**，也没有安装时的权限确认流程。
- **审核不一致**：微软侧以条款与举报为主，Open VSX 长期靠社区举报，
  2026 年才开始上发布前验证框架（命名空间仿冒、泄露凭据、恶意模式、可疑上传隔离）。
- **排名信号失真**：安装量单调递增、评分不过期，两个指标都在描述过去。
- **无依赖治理**：`extensionDependencies` 本来是便利功能，现在是投递通道，
  生态里没有依赖审计工具。

## 6. 整体特点（七条）

1. **平台方是最大开发者**，既是裁判又是选手，规则与产品同源。
2. **头部极集中、长尾极长**，安装量分布接近幂律，绝大多数扩展从未被有效发现。
3. **协议化（LSP/DAP）解耦了能力**，让"扩展"退化成胶水和 UI，降低了垄断可能。
4. **存在稳定的"验证 → 内置 → 吸收"循环**，通用能力做对了就会被吞。
5. **质量信号全部是历史值**，安装量只增不减、评分不随时间衰减，用户无从判断当前状态。
6. **安全模型是"信任所有扩展"**，无权限声明、无运行时沙箱、默认自动更新。
7. **AI 正在改变扩展的定义**：从"给编辑器加功能"变成"给 agent 供能力"。

## 7. 发展趋势

### 7.1 扩展形态：从"加功能"到"供能力"

2025–2026 年 VS Code 的 AI 扩展性阶梯基本成型［官，1.109–1.118 release notes］：

| 层级 | 能力 | 状态 |
| --- | --- | --- |
| 补全 | Inline Completion Provider | 稳定 |
| 对话 | Chat Participant（`@name`） | 稳定 |
| 调用模型 | Language Model API | 稳定 |
| 被 agent 调用 | Language Model Tool（`lm.registerTool`） | 稳定 |
| 供模型 | Language Model Chat Provider（BYOK） | 1.117 稳定 |
| 供工具 | 扩展内嵌 MCP Server（`registerMcpServerDefinitionProvider`） | 稳定 |
| 供人格/技能 | Custom Agent（`.agent.md`）、Agent Skills（`SKILL.md`） | 1.109 GA |
| 打包交付 | Agent Plugins（`plugin.json` 捆绑 skills/commands/agents/MCP/hooks） | 预览 |

**方向很清楚**：扩展的价值从"我提供 UI"迁移到"我提供 agent 能调用的能力"。
最底层甚至不需要写代码——一个 markdown 文件就是扩展。

### 7.2 无代码扩展放大了攻击面

`.agent.md` / `SKILL.md` 的引入意味着扩展可以**不含任何可执行代码却改变 agent 行为**，
这直接引入提示注入类风险，而传统静态扫描对此无效。

### 7.3 注册表侧前置验证 + 组织级白名单

Open VSX 2026 年上的发布前验证框架是行业信号：**登记即信任**的时代结束了。
配套措施在组织侧成型：组织级扩展白名单、自动更新冷却期、按扩展追踪进程（如
Cursor 注入 `CURSOR_SPAWNED_BY_EXTENSION_ID` 环境变量便于溯源）。

### 7.4 平台分化

Open VSX 从"边缘镜像"变成 AI-native IDE 的共同底座（Cursor、Kiro、Antigravity、Windsurf 都建在上面），
2026 年 1 月起对 >75 req/s 的组织收费，AWS 战略投资、迁移欧洲多区域。
同期 VS Code 在部分人群中的份额在下滑（Rust 开发者三年从 61.7% → 51.6%，Zed 升至 18.6%）［研］。

### 7.5 依赖链成为主战场

攻击从"直接投毒"→"凭据窃取后自传播"→"滥用依赖声明传递投递"。
防御重心也随之从"审核单个包"转向"管控整条依赖链"。

### 7.6 权限模型是被推着走的

至今没有 manifest 权限声明，但压力在累积：蠕虫级事件、企业合规要求、
AI 扩展对代码库的深度访问。**这可能是下一次平台级变更的触发点**——
谁先把"可声明的权限 + 安装时告知 + 运行时强制"做出来，谁就拿到企业市场的信任。

## 8. 对 Qing Notepad 插件机制的启示

对照本仓库 `docs/plan-plugin-system.md` 的定案，逐条映射：

| VS Code 的教训 | 我们的对应设计 | 评价 |
| --- | --- | --- |
| extension host 只做崩溃隔离 | 双轨：Worker 物理无 IPC + 独立窗口按 label 收窄 capability | 补上了 VS Code 缺的那一半 |
| 默认自动更新放大蠕虫 | D4：不自动更新，权限扩大必须重新授权 | 直接对应 GlassWorm 的投递路径 |
| manifest 无 permissions 字段 | `permissions` 声明 + 安装时逐条告知 + 可单独撤销 | 生态里少见的做法，是差异化点 |
| 安装量单调递增、评分不过期 | 索引不做下载量排行，只给「最近更新 + 兼容区间」 | 避免复制失真信号 |
| 双注册表命名空间抢注 | 单一索引 + `id` 全局唯一且安装后不可变 | 结构上不存在抢注面 |
| `extensionDependencies` 被滥用 | D6：v1 直接拒绝非空 `dependencies` | 与 2026 年攻击面完全错开 |
| LSP/DAP 让能力可替换 | v1 只开 commands/views，不碰编辑器 schema | 印证 A 档决策是对的 |
| 通用能力会被平台吸收 | 生态定位应只做「宿主不打算做」的事 | 需要写进开发者文档，管理作者预期 |

**三条可执行结论**：

1. **把"权限可见"当成产品卖点而不是合规负担**。VS Code 至今做不到，这是我们唯一能在
   插件机制上建立口碑的地方。安装弹窗的权限文案值得单独立项打磨。
2. **索引里不要出现下载量**。一旦有排行，作者就会刷量（GlassWorm 就干过人为刷下载），
   而我们没有反刷能力。改为展示「最后更新时间 / 支持宿主版本 / 权限数量」。
3. **开发者文档必须写清"什么不该做成插件"**。VS Code 的作者被吸收循环反复教育过，
   我们提前写清，能省掉后期大量无效 PR。
