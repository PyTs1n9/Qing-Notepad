# 窗口贴合（window binding）

两个窗口挨得够近时，双击它们之间的缝，把二者成组：移动或缩放一方，另一方跟着走。
再次双击同一条缝解绑。

**作用范围只有本应用自己的顶层窗口**（`main` 与 `note-window-*`）。第三方窗口不在承诺内，
原因见 D3。

## 结论

| 编号 | 结论 | 理由 |
| --- | --- | --- |
| D1 | 成组关系由 Rust 侧的 `window_binding.rs` 持有，前端只发起请求和画接缝线 | 窗口矩形是物理像素（`outerPosition`），鼠标坐标是 CSS 像素（`clientX`），150% 缩放下差 1.5 倍。换算放在前端等于把同一件事写两遍，且笔记窗口不读 `settingsStore`，拿不到统一状态 |
| D2 | 双击落点判定 = 「前端粗筛窗口内边带（12px）→ Rust 按真实矩形精确判定」 | 全局低级鼠标钩子能直接拿到屏幕坐标，但那会把整个应用的鼠标延迟押在钩子回调上，还要承担 AV 误报与提权窗口的一整套问题。粗筛把开销摊到零：绝大多数双击在第一层就被丢弃 |
| D3 | 不做跨进程窗口（第三方应用） | 成组必须能自由改写对方的位置与尺寸：提权进程的窗口非提权进程写不动（UIPI）、`WM_GETMINMAXINFO` 会让对方拒绝变小、自绘边框窗口的可见边界与逻辑矩形不一致。三条都是无解或需要提权助手进程，超出「笔记软件顺手做的事」 |
| D4 | 一个窗口同时只属于一组，最多两窗 | 三窗以上要处理「拖共享边时整列重排」，规则会膨胀一个量级，而且没有可验的判定标准 |
| D5 | 传播只按「当前几何 + 成组时记下的偏移」重算绝对落点，不累加增量 | 逐帧累加在拖动抖动、系统夹紧、DPI 取整下都会漂；绝对公式每次从零算，拖多久都不偏 |
| D6 | 自己写出去的位置用「预期表」辨认，认不出来才算用户操作 | `SetWindowPos` 必然回流成窗口事件。用布尔标志会在嵌套移动里漏；预期表按 `(label, rect, 时间戳)` 比对，`Resized` 紧跟 `Moved` 也能一并吸收 |
| D7 | 缩放一方时，另一方只平移、不改尺寸 | 改尺寸会撞上对方的最小尺寸（笔记窗口 560×420），夹紧逻辑分叉多且无法在无 GUI 环境验证。平移在所有情况下都成立 |
| D8 | 跨显示器/跨 DPI 不成组，已成的组在 DPI 变化时拆开 | 物理像素偏移只在同一缩放比例下守恒；不拆会把窗口拖成错位 |
| D9 | 顶栏 34px 以内不参与判定 | 顶栏双击是系统的「最大化」。贴合抢这块会把最常用的手势变成意外 |

## 几何约定

- `a` 永远是左/上那一个，`b` 是右/下那一个 —— 传播公式因此只有两套。
- `gap = b 的起始边 − a 的结束边`，0 表示严丝合缝；允许压到 −30 物理像素。
  为什么允许负值：`decorations: false` 并不消除外框，每侧仍有约 11px 不可见缩放边框
  （`topics/ui-rules.md` §5 实测 22×13）。用户照着"看得见的边缘"对齐时，两个外框会
  互相压住约 22px —— 只允许 3px 压边会把最自然的摆法判成"不是一条缝"。
- `offset` = 缝的垂直方向上的偏移，成组那一刻固定。
- 缝两侧至少要有 48px 的共享边（`MIN_SEAM`），否则两个窗口只是擦肩而过。
- 对面那条边离自己这条边 ≤ 24px（按 DPI 放大）才算「贴得够近」。

## 解绑条件

- 再次双击同一条缝（切换）。
- 任一成员销毁、最小化、最大化。
- 两者 DPI 不再相同。
- 调用 `window_binding_release`（不带 label 时释放全部）。

## 已知限制

- 双击必须落在**某个窗口内**、且距靠缝的那条边 ≤12px。缝本身若宽过 24px，中间那段是桌面，
  双击它谁也收不到（没有全局钩子就没有坐标）。这是 D2 的直接代价。
- 拖动中的同步依赖 `WindowEvent::Moved` 的到达频率。窗口管理器在模态拖动循环里可能合批，
  表现为跟随略有滞后，不会错位。
- 拖拽、流式、时序类行为本机无 GUI 无法自动验收，见 `topics/verify-runbook.md`。

- 是否把贴合状态持久化到下次启动。
